# Уроки с реального проекта — почему протокол устроен именно так

Каждый пункт ниже — не абстрактное «лучшая практика», а конкретный баг процесса, который реально
произошёл в проекте-примере (MeetingTranscriber) и был исправлен. Если в новом проекте покажется,
что какое-то правило избыточно — вспомните, что оно появилось не просто так.

## 1. Никогда не доверять самоотчёту исполнителя

**Что случилось:** исполнитель несколько раз писал `status: done` в статус-файле, при этом либо не
сделав реальный commit кода вообще, либо не закоммитив финальную правку отчётности. Раздел
«Проверка» в отчёте писал «сборка прошла успешно» без привязки к реальному выводу — и реальные баги
(краши приложения при живом использовании, неверные пути к скриптам) проходили собственную проверку
исполнителя незамеченными.

**Принцип:** оркестратор после каждого «done» ОБЯЗАН: (а) проверить `git log -1 --stat` и
`git status --short` независимо, (б) прочитать изменённый код по существу, а не только диффстат,
(в) независимо пересобрать/протестировать, (г) там, где применимо — реально запустить и вручную
проверить результат (не просто «код выглядит правильным»). Самопроверка моделью, которая сама
писала код, ненадёжна структурно — у неё те же слепые пятна, что и при написании.

## 2. Порядок «коммит → потом отчётность» гарантированно теряет отчётность

**Что случилось:** более ранняя версия инструкции предписывала сначала закоммитить код, потом
дописать `REPORT.md`/`STATUS.md`/`LOG.md`. Естественно, эта последняя правка регулярно оставалась
некоммиченной — инструкция сама создавала баг.

**Принцип:** сначала ВСЯ отчётность дописывается, коммит — строго последним действием. Если после
коммита `git status` не пуст — это повод сделать ещё один коммит, не оставлять хвост. Это тот
редкий случай, когда порядок шагов в инструкции — не деталь, а сама суть бага.

## 3. Файлы-логи, которые «только дописываются», должны быть от этого защищены явно

**Что случилось:** файл истории действий был один раз полностью перезаписан вместо дозаписи —
исполнитель, чей инструмент записи файла не умел чисто аппендить, записал «весь файл» как одну
новую строку, потеряв всю историю. Восстанавливали из git.

**Принцип:** явно указать в протоколе — если инструмент записи не умеет append, сначала прочитать
текущее содержимое целиком, затем писать `<прочитанное> + <новая строка>`. И явный чек: если после
записи количество строк уменьшилось — это гарантированный баг, стоп.

**(Обновление, версия протокола 1.4.0):** файл, о котором шла речь (`LOG.md`), позже убрали из
протокола целиком как избыточный третий файл отчётности при живом `STATUS.md` и `git log` (см.
пункт про упрощение отчётности ниже, если он появится, или сам факт — `LOG.md` больше нет в
`aiac/templates/`). Сам принцип защиты append-only файла от случайной перезаписи не устарел — он
переехал на `REPORT.md`, единственный оставшийся append-only файл отчётности.

## 4. Точные строки вывода вместо пересказа

**Что случилось:** отчёты писали «сборка прошла успешно» без доказательства. Оркестратор всё равно
каждый раз перепроверял сам — то есть пересказ не экономил вообще ничего, только создавал ложное
чувство проверенности.

**Принцип:** отчёт должен содержать **дословную строку** из реального вывода команды (`** BUILD
SUCCEEDED **`, `Executed N tests, with 0 failures` и т.п.), а не своими словами. Это не улучшает
доверие к отчёту само по себе (см. пункт 1 — оркестратор всё равно проверяет), но резко снижает
шум и помогает быстро сверить ожидание с фактом без повторного запуска, если нужно всего лишь
убедиться, что конкретно эта команда была выполнена.

## 5. Неявные развилки в задаче решаются непредсказуемо

**Что случилось:** несколько раз задача, сформулированная без явного указания «как именно» при
наличии нескольких валидных путей реализации, приводила к решению, которое потом приходилось
переделывать или которое расходилось с ожиданием.

**Принцип:** если у оркестратора есть понимание, что задачу можно сделать несколькими способами и
есть предпочтительный — указать его явно, с обоснованием, в самой задаче. Не полагаться на то, что
исполнитель «сам разумно выберет».

## 6. Общее рабочее дерево = гонки правок между оркестратором и исполнителем

**Что случилось:** оркестратор и исполнитель работали в ОДНОЙ и той же папке на диске (не в
изолированных копиях). Пока исполнитель работал в фоне, любая правка оркестратора в те же файлы
(даже невинная документация) рисковала попасть не в ту ветку, потеряться при следующем `git checkout`
исполнителя, или наоборот — перезаписать то, что исполнитель ещё не закоммитил.

**Изначальный принцип был дисциплинарным** («оркестратор не трогает файлы, пока исполнитель
активен», проверять `ps aux` перед правкой) — он снижал частоту проблемы, но не устранял её
структурно: одно забытое исключение — и гонка снова возможна.

**Обновлённый принцип (структурный, не дисциплинарный): каждая задача исполнителя выполняется в
своём собственном `git worktree`, а не в основном рабочем дереве.** Перед запуском исполнителя
оркестратор создаёт изолированную копию рабочего дерева под конкретную ветку задачи:

```
git worktree add .worktrees/<branch> -b work/<branch>   # новая ветка
git worktree add .worktrees/<branch> work/<branch>       # ветка уже существует — не сбрасывать её
```

и запускает исполнителя с рабочей директорией `.worktrees/<branch>`, а не в корне проекта. Пока
исполнитель работает там, оркестратор свободно читает/правит основное рабочее дерево (`PLAN.md`,
`STATUS.md` и т.п. в его собственной копии) — физической гонки за одни и те же файлы на диске больше
нет, потому что это буквально разные каталоги, указывающие на разные ветки одного репозитория.
После успешного мержа ветки задачи — `git worktree remove .worktrees/<branch>` (и опционально удалить
саму ветку), не оставлять висящие worktree-каталоги. `.worktrees/` добавляется в `.gitignore` с
самого начала (см. `BOOTSTRAP.md`, Шаг 5).

Это же решение открывает путь к **нескольким одновременным исполнителям** — каждый в своём
worktree, над своей веткой/задачей. Единственное жёсткое ограничение, которое остаётся: не запускать
два процесса над ОДНИМ и тем же worktree/веткой одновременно — это по-прежнему гонка, просто
локальная к одному каталогу, а не ко всему репозиторию.

## 7. Файл текущей задачи с растущим номером, не переиспользуемое имя

**Что случилось:** пока файл задачи назывался всегда одинаково (`TASK.md`, перезаписывается каждый
раз), по логам и списку файлов было невозможно на глаз понять, какой по счёту раунд выполняется —
приходилось читать содержимое. Переход на `TASKn.md` с растущим номером (ровно один файл в любой
момент, старый удаляется при создании нового) решил это — заодно один раз поймали баг, когда старый
файл забыли удалить (два файла задачи одновременно, путаница).

**Принцип:** номер в имени файла — дешёвый, но реально полезный сигнал прогресса, читаемый без
захода внутрь файла. Проверять `ls TASK*.md` — должен быть ровно один.

**(Обновление, версия протокола 1.3.0):** сам принцип (монотонный номер, никогда не переиспользуется)
не изменился, но физическое расположение — да: файлы задач теперь живут в
`tasks/{pending,in_progress,done}/`, а не единственным файлом в корне (см. «Конвенция задач» в
`AGENTS.md`) — это понадобилось, чтобы поддержать несколько параллельных исполнителей (см. пункт 6).
`ls TASK*.md` в корне больше не актуален как проверка.

## 8. Калибровать частоту проверки фоновых задач по их объёму

**Что случилось:** оркестратор поначалу проверял прогресс исполнителя каждые несколько минут вне
зависимости от того, насколько объёмная задача — это тратило впустую ресурсы оркестратора на
проверки, которые почти всегда просто подтверждали «ещё работает».

**Принцип:** маленькая задача — первая проверка через ~10 минут; средняя — 15-20; тяжёлая (внешние
репозитории, установка тяжёлых ML-зависимостей, конвертация моделей) — 20-30+ минут, с готовностью
подождать ещё, если процесс явно жив (например, активно грузит CPU) и не завершился с ошибкой.

## 9. Никогда не изобретать системные/библиотечные API по памяти

**Что случилось:** дважды в проекте появлялся правдоподобный, но полностью несуществующий код —
имена функций/типов, которые «должны были» существовать по аналогии, но не существовали в реальном
API. Каждый раз это стоило часов отладки при том, что сверка с реальным источником заранее заняла бы
минуты.

**Принцип:** если задача касается малодокументированного, редкого или быстро меняющегося API —
эталонный источник (официальный репозиторий, актуальная документация) указывается в задаче явно, и
исполнителю прямо говорится сверяться с ним, а не писать по аналогии/памяти. Если источник
недоступен — зафиксировать `blocked`, не гадать. Это особенно актуально для быстро развивающихся
библиотек (в проекте-примере — сама версия установленной библиотеки для диаризации оказалась новее
той, на которую опирался существующий код, с реально другим API — не выяснилось бы без сверки на
живом окружении).

## 10. Файлы самого скелета `aiac/` не должны попадать под маски, которые ищет исполнитель

**Что случилось:** при тестовом прогоне самого этого скелета на игрушечном проекте исполнитель
получил инструкцию «найди файл по маске `TASK*.md` в корне проекта», и его собственный Glob-инструмент
рекурсивно нашёл ДВА совпадения: реальный `TASK1.md` и `aiac/templates/TASK.template.md` (имя файла
шаблона тоже начинается на `TASK` и заканчивается на `.md`). В этот раз исполнитель не ошибся —
прочитал оба, но опёрся на правильный, — но это ровно тот тип неявной развилки, от которого
предостерегает пункт 5: результат зависел от того, что конкретная модель в конкретный момент решила
считать «актуальным». Простое `ls TASK*.md` в корне (нерекурсивно) эту коллизию не показывает, а вот
рекурсивный поиск (Glob-инструменты у большинства агентных CLI по умолчанию рекурсивны) — показывает.

**Принцип:** ни один файл внутри `aiac/` (сам скелет остаётся в новом проекте как справочник — см.
`README.md`) не должен своим именем совпадать с масками, по которым протокол ищет «текущий» файл
состояния (`TASK*.md` — единственная такая маска в этом протоколе). Отсюда шаблон файла задачи назван
`CURRENT_TASK.template.md`, а не `TASK.template.md`. Если в будущем в протокол добавится ещё одна
маска для поиска, сразу проверьте, не пересекается ли она с именами файлов внутри `aiac/`.

**(Обновление, версия протокола 1.3.0):** с переходом на `tasks/{pending,in_progress,done}/`
(см. пункт 6, «Конвенция задач» в `AGENTS.md`) поиск задачи больше не идёт по маске от корня — файл
вычисляется по имени текущей ветки (`tasks/in_progress/<слаг из work/...>.md`), что заодно убирает и
этот класс коллизий: путь однозначен, глобом искать не нужно вообще.

## 11. Без `.gitignore` с самого первого коммита первая же задача затягивает в git мусор

**Что случилось:** при том же тестовом прогоне бутстрап-протокола (пункт 10) исполнитель на первой
же реальной задаче закоммитил вместе с кодом скомпилированные `__pycache__/*.pyc` — просто потому что
`.gitignore` в репозитории ещё не существовало на момент коммита. Исполнитель сам это заметил и
исправил следующим коммитом (`git rm` мусора + добавление `.gitignore`) — то есть до чистого
`git status --short` в итоге дошли, но сами бинарники остались в истории git навсегда, и это сработало
только потому, что конкретная модель в этот раз проявила внимательность, а не потому что протокол это
гарантировал.

**Принцип:** `.gitignore`, соответствующий выбранному стеку, создаётся ДО первой задачи, в рамках
самого бутстрапа (Шаг 5) — вместе с `git init`, а не как что-то, что исполнитель должен додумать сам
при первом же коммите. Это дёшево сделать заранее и дорого чинить постфактум (следы в истории git
остаются).

## 12. Секреты и конфиденциальные данные — риск того же типа, что и мусорные файлы, но дороже

**Что случилось:** проект-пример (MeetingTranscriber) с самого начала был задуман для записи
конфиденциальных переговоров — это стало отдельным разделом плана («6. Продакшен-готовность для
конфиденциальных переговоров»). Реальный токен для доступа к Hugging Face передавался человеком
напрямую в чат с оркестратором, а сохранялся не в файл репозитория, а в `UserDefaults` (системное
хранилище настроек) — то есть в git он никогда не попадал. Это сработало, но по чистой
дисциплинированности процесса в моменте, а не потому что протокол на тот момент требовал этого явно
— явного универсального правила «секреты никогда не в отслеживаемых git файлах» тогда не было.

**Принцип:** тот же класс риска, что и мусорные файлы сборки (пункт 11), только с несравнимо более
высокой ценой ошибки — попавший в git секрет считается скомпрометированным навсегда, даже после
удаления из текущей версии, и требует ротации, а не просто `git rm`. Это должно быть закрыто на
трёх уровнях, а не понадеявшись на аккуратность конкретного раунда работы:
- на бутстрапе — явный вопрос человеку о том, какие секреты будут в проекте и как их хранить
  (`BOOTSTRAP.md`, Шаг 0.2), плюс `.gitignore` с типовыми секрет-путями с первого коммита;
- для существующего проекта, который только подключают к процессу — аудит уже накопленной истории
  git на предмет уже утёкших секретов ДО того, как процесс вообще начнёт что-либо коммитить сверху;
- на каждой задаче — исполнитель обязан проверять свой же diff на секреты перед каждым коммитом
  (`AGENTS.md`, раздел «Секреты и конфиденциальные данные»), а не полагаться на то, что просто не
  напишет секрет по невнимательности.

## 13. Поле «Коммиты:» в `REPORT.md` не может ссылаться само на себя

**Что случилось:** первый настоящий end-to-end прогон протокола (dogfood-тест на игрушечном
проекте, исполнитель — opencode с бесплатной моделью). Исполнитель написал в `REPORT.md` плейсхолдер
`<хэш будет добавлен после коммита>`, закоммитил код вместе с отчётом, а затем сделал ОТДЕЛЬНЫЙ,
второй коммит специально для того, чтобы вписать в `REPORT.md` реальный хэш первого коммита — ровно
то, что этот же шаблон прямо запрещал делать. Формально задача была выполнена корректно (тесты
проходят, `git status` чист), но появился лишний коммит только ради одного текстового поля.

**Принцип:** проблема была не в невнимательности модели, а в самом шаблоне — он просил указать
хэш коммита, который содержит этот же `REPORT.md`, а такой хэш физически не может быть известен до
создания коммита. Нельзя запрещать «не угадывай и не дописывай отдельным коммитом», не давая
альтернативы — модель находит обходной путь сама, и не факт, что такой же безобидный. Правильная
формулировка: поле «Коммиты:» ссылается только на коммиты ДО текущего (если они были), а не на сам
финальный коммит — оркестратор в любом случае видит его хэш на ревью через `git log -1 --stat`, в
самом отчёте это не нужно.

## 14. Наивный `nohup ... &` поверх фонового примитива оркестратора даёт ложный сигнал «готово»

**Что случилось:** в том же dogfood-прогоне оркестратор (Claude Code) запускал исполнителя, обернув
команду в собственный `nohup opencode ... &`, поверх уже имеющегося у среды оркестратора примитива
фонового запуска команд. Среда восприняла как «команду» сам обёрточный shell-скрипт
(`cd ... && nohup ... & echo pid`), который завершается почти мгновенно после запуска фонового
процесса — и вернула сигнал «команда завершена», хотя реальный процесс исполнителя работал в фоне
ещё несколько минут (проверено — процесс был жив в `ps aux`). Оркестратор едва не начал проверять
результат исполнителя до того, как тот реально закончил работу.

**Принцип:** запускай команду исполнителя напрямую через фоновый примитив своего инструментария
(например, встроенный фоновый режим Bash-тула у Claude Code), не оборачивай её дополнительно
вручную в `nohup`/`&` — иначе сигнал «готово» относится к обёртке, а не к реальному процессу
исполнителя. Если обёртка технически неизбежна (например, ради редиректа вывода в конкретный файл
в среде, где нет другого способа) — не доверяй факту возврата управления шеллу как признаку
завершения: отслеживай реальное завершение по PID (`kill -0 <pid>`, дожидаясь его исчезновения)
отдельным шагом ожидания.
