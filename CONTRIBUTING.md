# Как участвовать

Репозиторий документационный: кода приложения тут нет и не появится, всё содержимое `src/` —
это протокол и шаблоны к нему. Изменения приветствуются, но почти каждое из них меняет поведение
чужого агента, поэтому к ним предъявляется больше требований, чем к правке обычного README.

## Проверки перед отправкой

```bash
./scripts/check-package.sh   # версии совпадают, все файлы протокола попадут в пакет
./scripts/install-test.sh    # установщик не ломает существующие проекты (сеть не нужна)
```

Обе проверки выполняются в CI на каждом PR, вторая — на локальных правках установщика, первая —
обязательно перед `npm publish` (она же вызывается из `prepublishOnly`).

## Что нужно обновить вместе с изменением протокола

1. **`src/VERSION`** и `version` в `package.json` — обязательно синхронно, иначе `check-package.sh`
   упадёт. Поднимается ли minor или major, решает характер изменения (см. ниже).
2. **`CHANGELOG.md`** — новая запись вверху. Версия, которая уже опубликована, не переписывается.
3. **`src/README.md`** — в нём есть карта содержимого `src/`. Если добавили, удалили или
   переименовали файл, поправь и её, иначе документация начнёт врать.
4. **Ссылки из шаблонов.** В `src/templates/` и `src/BOOTSTRAP.md` протокол ссылается сам на себя
   путями вида `aiac/templates/…` и `aiac/LESSONS_LEARNED.md`, пункт N. Если переименовали файл —
   grepните по этим ссылкам, иначе агент в подключённом проекте будет искать несуществующее.

## Версионирование

`src/VERSION` — версия **протокола**, а не упаковки.

- **patch** — формулировки, уточнения, исправления опечаток, новые разделы в шаблонах, которые
  ничего не меняют в поведении.
- **minor** — новое правило или новый шаг протокола, обратная совместимость сохраняется: старый
  `PLAN.md` и `AGENTS.md` в подключённых проектах остаются работоспособными.
- **major** — меняется контракт: переименование файлов протокола, изменение схемы `STATUS.md`,
  смена конвенции задач. Обязательно опишите в changelog, что именно нужно сделать в уже
  подключённых проектах, и поднимите это в `BOOTSTRAP.md`, чтобы новый бутстрап это учёл.

Правило совместимости по умолчанию строгое: `aiac/` в подключённом проекте обновляется через
`--force`, и потеря совместимости ломает чужой проект молча, без ошибки, — именно поэтому
ломающие изменения и выделяются в major.

## Соглашения по содержанию

- Русский язык по умолчанию (протокол настраивает язык общения в проекте, но сам текст — русский).
- Тон: конкретно и без рекламы. Лучше «это не работает, потому что X, см. урок N», чем «мощный
  и гибкий подход к задачам».
- **Каждое нетривиальное правило ссылается на урок в `src/LESSONS_LEARNED.md`.** Правило без
  истории возникновения, как правило, означает выдумку, а не проверенный опыт: непонятно, чем оно
  ломается. Новый урок — это запись в `LESSONS_LEARNED.md` с пометкой, из какого бага он вырос.
- Не выдумывайте то, чего не проверяли. Если утверждение о работе стороннего инструмента не
  проверено — либо проверьте, либо сформулируйте как «по опыту автора», либо не пишите.

## Релиз

```bash
# 1. поднять src/VERSION и package.json до новой версии, дописать CHANGELOG, закоммитить в main
# 2. прогнать проверки локально
./scripts/check-package.sh && ./scripts/install-test.sh
# 3. создать тег — по нему публикация запускается сама
git tag v1.6.1 && git push origin main --tags
```

Workflow `.github/workflows/release.yml` на теге `v*` публикует пакет в npm (с provenance) и
создаёт GitHub Release с прикреплённым tarball. Требуется секрет `NPM_TOKEN` в настройках
репозитория и включённый Actions.

Номер тега должен совпадать с `version` в `package.json` — установщик по умолчанию ставит `main`,
а зафиксированный (`--ref v1.6.1`) должен указывать на существующий тег.
