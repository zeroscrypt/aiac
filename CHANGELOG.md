# Changelog

Проект следует [semver](https://semver.org/lang/ru/). Версия протокола живёт в `src/VERSION` и
должна совпадать с `version` в `package.json` — это проверяет `scripts/check-package.sh`, потому
что по тегу npm раздаётся установщик, а `aiac/VERSION` попадает в подключённый проект.

Число `1.6.0` — это версия **протокола** (содержимого `src/`), а не версия упаковки. Упаковка и
доставка не имеют отдельной нумерации: они меняются только тогда, когда меняется протокол.

## [1.6.0] — 2026-09-27

### Протокол

- **Уровень детализации задачи масштабируется с риском, а не одинаков для всех задач.** Урок 15
  в `LESSONS_LEARNED.md`. Оркестратор на каждой задаче заново решает, насколько подробно её
  расписать, и поднимает детализацию до почти готового алгоритма при сигналах повышенного риска:
  история багов/крашей в этой части кода, конкурентность, системные/аппаратные API, высокая цена
  ошибки постфактум. Обычный уровень (что сделать + явно решённые неочевидные развилки) для задач
  без этих сигналов остаётся достаточным — псевдокод для каждой мелочи тратит токены оркестратора,
  не снижая риска.

### Публикация

- Первая публикация на npm как [`aiac`](https://www.npmjs.com/package/aiac) (`Apache-2.0`).
- Установка одной командой через `install.sh` (`curl … | bash`), вместо ручного копирования папки.
  Установщик кладёт протокол в `<проект>/aiac/` и создаёт `CLAUDE.md` только если его нет;
  существующие `CLAUDE.md`/`AGENTS.md`/`PLAN.md` не перезаписываются никогда.
- `scripts/check-package.sh` — проверка перед публикацией: совпадение версий, наличие всех файлов
  протокола в tarball, отсутствие мусора.
- `scripts/install-test.sh` — сквозной тест установщика, без сети: раскладывает протокол в
  свежие проекты и проверяет, что он ничего не ломает по дороге.
- CI: проверка пакета и тест установщика на каждом PR; публикация по тегу `v*` с provenance.

## До 1.6.0 — 2026-09-20 … 2026-09-21

До первой публикации версии не проставлялись тегами, поэтому ниже — фактическая
последовательность коммитов, а не придуманная разбивка на версии. Якоря, которые документация
протокола называет явно (1.3.0, 1.4.0, 1.5.0), отмечены.

- Скелет протокола: `src/` с `README.md`, `VERSION`, `BOOTSTRAP.md`, `LESSONS_LEARNED.md` и
  шаблонами; базовый `.gitignore`.
- **Изоляция заменена с дисциплинарной на структурную** (урок 6): каждая задача исполнителя
  выполняется в своём `git worktree`, отсюда же — возможность нескольких исполнителей одновременно.
- Правила экономии токенов оркестратора: не читать проект целиком, если это может сделать
  исполнитель; ревью — по диффу, а не по всему дереву.
- Архивация `REPORT.md`/`LOG.md` по фазам Roadmap.
- Обоснование технических решений вынесено из `PLAN.md` в отдельные ADR-файлы.
- Версия протокола (`src/VERSION`), штампаемая в `CLAUDE.md` проекта, — чтобы будущие сессии
  замечали обновление протокола; fallback-исполнитель; supply-chain аудит на бутстрапе; эскалация
  конфликтов мержей человеку.
- **Урок 13** и **урок 14** — по итогам первого живого end-to-end прогона (dogfood на игрушечном
  проекте): исполнитель делал лишний коммит ради поля «Коммиты:» в собственном отчёте, а запуск
  через самодельную `nohup … &` обёртку давал ложный сигнал «процесс завершился».
- Тест на новую функциональность стал обязательным в Definition of Done.
- `STATUS.md` переведён в строгий YAML с фиксированной схемой из пяти полей.
- **1.3.0** — конвенция `TASKn.md` заменена очередью задач в `tasks/{pending,in_progress,done}/`
  (урок 7). Побочно ушёл урок 10: файлы скелета больше не могут совпасть масками поиска.
- **1.4.0** — `LOG.md` убран как третий файл отчётности.
- Definition of Ready: задача проверяется на готовность до запуска исполнителя.
- Описано поведение оркестратора при `blocked` / `failed`: перезапуск в том же worktree, ответ по
  существу вопроса, эскалация человеку.
- Уточнено восстановление после перезапуска сессии оркестратора: `STATUS.md` + `LOG.md` в worktree
  дают полную картину, даже если финальный коммит не сделан.
- Периодическая сверка с человеком по контрольным точкам (каждые 3-5 задач или на закрытии пункта
  Roadmap) — чтобы процесс не уехал в автопилот.
- **1.5.0** — `LOG.md` возвращён: снимок состояния и пошаговая история отвечают на разные
  вопросы, и при обрыве процесса до финального коммита `STATUS.md` показывает только последнее
  действие.
